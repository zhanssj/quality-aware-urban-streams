# Работа блоками: предложенное обновление процесса

Это предложение рабочего режима для владельца и следующий готовый prompt, не уже внесённые
изменения в GitHub. Численные результаты CI взяты из прочитанных логов; будущие метрики не получены.

## Приёмка по результатам, а не по каждой внутренней задаче

| Блок | Состав | Результат для внешнего ревью |
|---|---|---|
| B01 | T02 + T03 | Причинные признаки, три baseline, оценщик, первый bounded train/validation |
| B02 | T04 + T05 | Единый симулятор потерь/доставки/ожидания и небольшое сравнение сценариев |
| B03 | T06 | Валидационная матрица, ablation, performance, зафиксированный протокол |
| B04 | T07 | Финальный test-2025 и материалы статьи, только после отдельного разрешения владельца |
| Расширение | T08 | Потоковый стенд после ядра, отдельно назначается |

Эта группировка не переопределяет содержание T02-T08 и не разрешает все блоки сразу.
Соседний prompt назначает только B01. Перед B02/B03/B04 нужен новый конкретный scope.

## Внутри блока

Codex реализует и исправляет код, запускает тесты и отдельный review-проход самостоятельно.
Внутренние проверки остаются: не обучать реальные модели поверх непройденных тестов причинности.
Внешнее одобрение ChatGPT не требуется между T02 и T03, если блок явно назначен владельцем.
Несколько задач подряд не означает несколько одновременно пишущих в одни файлы агентов.

Для параллельной работы сначала стабилизируются контракты. Один исполнитель может писать
feature pipeline, второй - независимые проверки и оценщик. Один ответственный интегрирует
результат. В маленьком Python-core разумно сначала использовать одного исполнителя и отдельный
review-проход; дополнительный orchestrator не является целью исследования.

## Когда ревью блокирует

Блокируют следующий этап: утечка будущего/target, fit на validation/test, неверные метрики,
разный target set без объяснения, изменение масок/сетки, потеря данных, непрошедшие обязательные
тесты, секреты в артефактах, недостоверные заявления о выполненных запусках.
Не блокируют развитие сами по себе: именование, формат README, косметика, желательная
универсальность за пределами явно согласованного input contract. Их записываем как follow-up.
Пограничный дефект оцениваем по реальному влиянию; опасный код не объявляем безопасным лишь
ради скорости. Если fix небольшой, он может идти вместе с очередным блоком до принятия результата.

После замечаний проверяющий смотрит fix и зависимые места, а не начинает весь проект с нуля.
CI выполняет механические проверки. Внешнее ревью сфокусировано на корректности метода и данных.

## Отчётность

Один блок: одна ветка, несколько логических commit, один handoff и компактный bundle.
Нужны base/head/code SHA, diff, команды, exit codes, конфиг, run IDs, ограничения и реальные метрики.
Не нужны повтор всех аудитов и дублирование полных логов по каждому подразделу.
